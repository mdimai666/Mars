# Harness и скиллы: архитектура под масштабирование

Статус: Phase 0 и Phase 1 выполнены (выбран вариант B — свой каталог и тулсет вместо MAF-провайдера).
Phase 2 (масштабирование каталога) — по запросу. Ноды — в `ai/AiSkillsMemoryNodesPlan.md`.
Связанные документы: `ai/AiChatGuide.md` (раздел «Память, скиллы и рабочая папка агента»).

## Итоги Phase 0 (диагностика, 2026-08-13)

- A/B-матрица (skills × access × промпт, DeepSeek-v4-flash, полигон CLI): **все комбинации работают**,
  включая slim-промпт + оба провайдера. Гипотеза «harness-провайдеры ломают модель» НЕ подтвердилась.
- Настоящие причины прежней регрессии: битые сохранённые сессии (assistant tool_calls без tool-ответов
  → 400 invalid_request; лечится санитаром `TryFindOrphanToolCalls`) и потерянный при рефакторинге
  аргумент `frontEditorSlug` в `BuildInstructions` (front-инструкции не инжектились вовсе).
- Вывод: гейт `EnableSkills` удалён, скиллы включены всегда.
- MAF `AgentSkillsProvider` отключён не из-за модели, а по архитектуре: `AgentSkillsSource.GetSkillsAsync`
  требует живой `AIAgent` в `AgentSkillsSourceContext` — источники нельзя использовать отдельно от
  провайдера; свой сканер SKILL.md даёт независимость и точку роста для поиска/роутинга.

## Итоги Phase 1

- Slim-промпт (ядро + память + правила скиллов), каталог `<available_skills>` в контексте.
- `AiSkillCatalog` (сканер SKILL.md, кастомные перекрывают bundled), `SkillsToolset`

  фронт (preload, сразу ReadFrontFile), страница поста (preload, GetOpenPage* + честный fallback).

## Проблема

1. Базовый промпт (`AiChatPrompts.BaseInstructions`) оброс инструментоспецифичными правилами
   (настройки, открытая страница, посты, SQL, фронт). Каждый новый инструмент раздувает контекст —
   не масштабируется.
2. Скиллы реализованы через harness-провайдеры MAF, но после регресса выключены по умолчанию
   (`EnableSkills = false`): на полигоне DeepSeek-v4-flash при включённых провайдерах отвечал
   пустым ходом без вызовов.
3. Тезис пользователя: в Qwen Code CLI тот же DeepSeek отлично работает со скиллами —
   значит, дело не в модели, а в нашем harness.
4. Найденный баг текущего дерева: `AiChatAgentService.RunChatAsync` вызывает
   `AiChatPrompts.BuildInstructions(option, pageContext)` **без третьего аргумента**
   `frontEditorSlug` (до регресса, в 83a5c12, передавал). Итог: инструменты фронта есть,
   инструкция по ним (правило 13) не инжектится вовсе. Часть симптома «ответил и остановился»
   на редакторе фронта объясняется этим.

## Как устроено у других (подходы)

### Qwen Code CLI (проверено пользователем на DeepSeek — работает)
- Прогрессивное раскрытие: в контексте только компактный список `name + description`
  (`<available_skills>`), полное тело — через инструмент `skill` (аналог `load_skill`).
- Для большого числа **инструментов** — deferred tools: в контексте ядро, остальное
  модель достаёт через `tool_search` (поиск по имени/ключевым словам).
- Никаких «approval»-обёрток вокруг чтения скиллов.

### MAF HarnessAgent 1.17.0 (наш стек)
- `AgentSkillsProvider` — реализация спеки agentskills.io: advertise (name+description
  в системном промпте) → `load_skill` → `read_skill_resource` → `run_skill_script`.
- Шаблон инжекции кастомизируется: `AgentSkillsProviderOptions.SkillsInstructionPrompt`
  (плейсхолдер `{skills}`); дефолт — английский, довольно директивный.
- **Важно**: по умолчанию `load_skill` требует approval (`DisableLoadSkillApproval = false`).
  Мы отключали approval только у file_access-провайдера, у скиллов — нет. Поведение harness
  при вызове требующего approval инструмента без настроенного approver — кандидат на причину
  регресса.
- Источники кастомизируются (`AgentSkillsSource`): файловые, in-memory, агрегатор,
  в перспективе MCP (`UseMcpSkills`).
- Наш прежний A/B был с изъяном: один флаг `EnableSkills` переключал **сразу два** провайдера
  (skills + file_access) — виновник пустых ходов мог быть любым из них, плюс английский
  шаблон поверх плотного русского промпта.

### Масштабирование на тысячи скиллов
Плоский список описаний в контексте не масштабируется (токены). Варианты:
1. **Deferred + search** (паттерн tool_search из Qwen CLI / Anthropic / OpenAI tool search):
   описаний в контексте нет (или минимум), модель ищет по каталогу инструментом поиска.
2. **Семантический поиск** (эмбеддинги) — в Mars есть Semantic Kernel; позже pgvector.
3. **Иерархия категорий**: список категорий → список скиллов категории → load.
4. **Детерминированный роутинг по контексту**: сервер сам вставляет нужный скилл, зная,
   где пользователь (страница, включённые опции) — модели вообще не надо искать.
   Это то, что просил пользователь: «для определённых страниц в контекст вставляются
   дополнительные инструкции, чтобы агент знал, что пользователь редактирует страницу
   и надо вызвать инструмент изменения контента поста».

Рекомендация — комбинация 4 (горячий путь, ноль затрат на discovery) + 1 (хвост).

## Целевая архитектура: три слоя контекста

### L0 — ядро (всегда в контексте)
Slim-промпт как в коммите 361b13f: стиль/терминал, «не выдумывай», ask_user,
проверка результатом, память (компактно) + правило «если задача попадает под скилл —
сначала load_skill». Никаких инструментоспецифичных инструкций.

### L1 — роутинг по странице/контексту (детерминированный preload)
`PageSkillRouter`: сигналы, которые уже есть на сервере (`pageContext` = URL админки,
`frontEditorSlug`, опции вроде `EnableSqlAccess`) → список скиллов, чьё **полное тело**
инжектится в инструкции на этот запуск (и включается соответствующий toolset — это уже есть):

| Сигнал | Скилл | Toolset |
|---|---|---|
| `/dev/front/editor/{slug}` | `mars-front-editor` | FrontToolset (есть) |
| `/Post/...` (страница редактирования поста) | `mars-open-page` | PageToolset (есть) |
| `EnableSqlAccess` | `mars-sql` (preload или подсказка) | SqlToolset (есть) |

Единый источник тел — SKILL.md (константы `FrontEditorInstructions` и т.п. удаляются из
`AiChatPrompts`). Роутер также чинит баг пункта 4 проблемы (slug снова участвует в контексте).

### L2 — discovery длинного хвоста
Инструменты каталога (новый `SkillsToolset`):
- `search_skills(query)` — поиск по name+description всего каталога, возвращает компактные
  описания топ-N; MVP — токенизированный substring-поиск по in-memory индексу;
- `load_skill(name)` — полное тело;
- опционально `list_skills` / featured top-N описаний в контексте (настройка).
Каталог: bundled `ai-skills/` + кастомные `<data>/ai/skills` (сканируем существующими
`AgentFileSkillsSource`/`AggregatingAgentSkillsSource` — источники можно использовать
**без** провайдера). Позже: эмбеддинги, DB/маркетплейс, MCP-скиллы.

## Реализация скилл-инструментов: вариант A или B

- **B (рекомендую)**: свой `SkillsToolset` (search/load/list) по образцу Qwen CLI;
  `AgentSkillsProvider` выключен совсем. Полный контроль над русскими инструкциями,
  нет approval-магии и экспериментальных неожиданностей. Доказанный паттерн (CLI).
- **A**: оставить MAF-провайдер, но: `SkillsInstructionPrompt` на русском,
  `DisableLoadSkillApproval/ReadSkillResourceApproval = true`, кастомный source
  с ограниченным подмножеством; `search_skills` — отдельным toolset-ом.
  Выбирать, если Phase 0 покажет, что провайдер не виноват, или когда понадобятся
  MCP-скиллы (`UseMcpSkills` живёт у провайдера).

Решение принимается после Phase 0.

### Phase 2 — масштабирование каталога

Цель: каталог на тысячи скиллов без раздувания контекста. Что ломается на масштабе:
плоский список описаний в промпте (1000 × ~30 токенов = 30K/запрос), substring-поиск
не ловит синонимы, папки на диске без метаданных неоткуда пополнять внешне.

**MVP (выполнено 2026-08-13):**

1. **Индекс с инвалидацией** — `AiSkillCatalog` держит распарсенный список в памяти
   (кеш сбрасывается лениво: `FileSystemWatcher` на обоих корнях, `IncludeSubdirectories`,
   `NotifyFilter = FileName|DirectoryName|LastWrite|CreationTime`, любой событие → кеш в null,
   перескан на следующем `GetSkillsAsync`). Правка скилла подхватывается без перезапуска.
2. **`tags` во frontmatter** — опциональная строка `tags: a, b, c`; участвуют в haystack
   `SearchSkills` и выводятся в выдаче поиска. Bundled-скиллы получили теги.
3. **Ограниченный listing вместо полного списка** — опции `AiChatOption`:
   - `MaxSkillsInContext` (int, default 10; 0 — список вовсе не показывается) — потолок
     описаний в системном промпте;
   - `FeaturedSkills` (csv имён) — всегда в контексте, первыми и в заданном порядке.
   `BuildContextListing`: featured → остальные по имени, до потолка; перелив дописывает
   «…и ещё N — ищи через SearchSkills». На малых каталогах (≤ потолка) поведение прежнее.
4. **Лимит выдачи поиска** — `SearchSkills` возвращает до 20 результатов (`MaxSearchResults`),
   хвост — «уточни запрос»; пустой запрос — первые 20 каталога, а не весь.
5. **Промпт** — в `SkillsInstructions` явное правило: в `<available_skills>` может быть не весь
   каталог, подходящий скилл ищем через `SearchSkills`.

**За MVP (по мере роста каталога/источников):**

1. Семантический поиск: эмбеддинги name+description+tags (Semantic Kernel), векторы в памяти,
   при росте pgvector; гибрид с substring по точным совпадениям.
2. Каталог как сущность Mars: таблица (name, description, tags, source, version, enabled),
   источники — bundled / custom / плагины / маркетплейс; индекс агрегирует источники.
   Триггер — появление внешнего источника, не раньше.
3. Внешние источники: скиллы из плагинов и каталога плагинов (галерея рецептов из roadmap),
   MCP-скиллы (MAF `UseMcpSkills` — тогда возвращаемся к варианту A только как к источнику).
