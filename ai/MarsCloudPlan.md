# План: Mars Cloud — managed-хостинг Mars (SaaS)

Дата: 2026-08-12. Контекст: [ServicesRoadmap.md](./ServicesRoadmap.md) (Уровень 4 — монетизация).
Статус: **черновик; 2026-09-03 приняты решения по составу и деплою — моно-репо Mars.Cloud,
см. там `ai/CloudInfraPlan.md`; реализация не начата**. Идея: сайт, где человек
регистрируется, оплачивает подписку за месяц, и ему автоматически поднимается его собственный
инстанс Mars.

## Ключевые принципы

1. **Мультитенантность в одном процессе — не делаем.** Mars instance-based (каждый сайт = свой
   инстанс с БД и `data/`), поэтому модель «клиент = отдельный Docker-инстанс» ложится без
   переделки платформы.
2. **Control plane + абстракция провайдера.** Свой управляющий сервис знает только интерфейс
   `IInstanceProvider` (`Create / Start / Stop / Delete / Upgrade`). Стартуем с реализации
   «Docker на одном большом VPS», позже добавляем «Hetzner Cloud API / Fly.io / Azure Container
   Apps» и переключаемся конфигом — биллинг и сайт не меняются.
3. **Догфудинг**: у Mars уже есть Docker-образ и setup-автоматизация через env-переменные
   (первый старт без ручного визарда) — провижининг клиентских инстансов опирается на готовое.
   (2026-09-03: контрол-плейн — не сам Mars, см. принцип 4.)
4. **Контрол-плейн — отдельный сервис CloudPanel** (пересмотрено 2026-09-03): кабинет,
   подписки и оркестратор — новый .NET-сервис (Blazor Web App, большинство страниц — режим
   WASM, + бэкенд Minimal API), лендинг и блог — отдельный статический сайт. Мотив:
   маркетинговый сайт (SEO, статика) и приложение (состояние, биллинг) — разной природы и не
   должны делить инстанс и жизненный цикл. Исходное решение «контрол-плейн — инстанс Mars»
   отменено.
5. **Идентичность — Keycloak, деплоится вместе с облаком.** Mars уже умеет подключаться к
   Keycloak: модуль `Mars.SSO` (`src/Mars.Modules/Mars.SSO`) — `KeycloakProvider`,
   `DynamicSsoProviderFactory` с драйверами keycloak/google/github/microsoft/mars, настройка
   через `OpenIDClientOption`, документация — `wwwroot/mars/docs/SSO/KeycloakProvider.startup.md`.
   Регистрация и мультипровайдерный вход (Google, GitHub и др.) — identity brokering на Keycloak;
   контрол-плейн-Mars доверяет ему через Mars.SSO.

## Как это обычно делают (два полюса)

- **«Один большой сервер»** — все клиенты как Docker-контейнеры на одном мощном VPS, перед ними
  reverse-proxy (Caddy/Traefik) с wildcard-доменом `*.marscloud.<домен>` и авто-TLS. Так стартует
  большинство indie-SaaS: дёшево, просто. Минусы: noisy neighbors, одна точка отказа, апгрейд
  сервера = даунтайм всех.
- **«Control plane + API провайдера»** — свой только управляющий сервис, инстансы поднимаются
  через API внешнего облака (Hetzner Cloud, DigitalOcean, Fly.io, AWS Fargate, Azure Container
  Apps, Google Cloud Run). Так делают взрослые: Supabase (control plane поверх AWS), Umbraco
  Cloud (инстанс = Azure Web App), Ghost Pro. Нет своего железа, масштабирование = вызов API.

Это не «или/или»: абстракция провайдера позволяет начать с первого и вырасти во второе.

## Из чего состоит продукт

1. **Сайт / личный кабинет** — сервис CloudPanel (принцип 4): страницы тарифов, кабинета,
   статуса инстанса, кнопка «открыть мой Mars». Вход/регистрация — через Keycloak (OIDC,
   Google/GitHub — брокеры; для инстансов клиентов в перспективе — драйверы `Mars.SSO`).
2. **Биллинг** — подписка. **Stripe** (Checkout + Billing + webhooks, PCI-зону не трогаете).
   Альтернатива для маленькой команды: **Paddle / Lemon Squeezy** как merchant of record — сами
   разруливают VAT/налоги по миру, снимают юридическую боль международных продаж.
3. **Оркестратор** — фоновая часть CloudPanel (тот же .NET-стек): слушает webhooks биллинга
   («оплачено» → поднять инстанс, «не оплачено» → приостановить, «отмена» → удалить после
   grace-периода) и дёргает `IInstanceProvider`.
4. **Провижининг инстанса** — почти всё готово: Docker-образ Mars + setup через env-переменные.
   Оркестратор запускает контейнер с env (админ-почта, строка подключения, URL) — инстанс сам
   себя настраивает при первом старте.
5. **DNS/TLS** — wildcard-поддомен на клиента, авто-сертификаты: на одном сервере — Caddy с
   on-demand TLS; на платформенных провайдерах (Fly/Container Apps) домены и TLS — часть
   платформы.
6. **Бэкапы** — обязательны для платного хостинга: ночной `pg_dump` каждой базы в объектное
   хранилище (R2/Wasabi/Hetzner Object Storage) + проверка восстановления.
7. **Жизненный цикл** — пауза за неуплату (контейнер останавливаем, данные не трогаем), апгрейд
   версии Mars (пересоздание контейнера с новым образом; EF-миграции применяются на старте),
   лимиты CPU/RAM по тарифу (`docker --cpus/--memory` или размер VM у провайдера).
8. **Админка оператора** — раздел в CloudPanel: список инстансов, логи, «зайти как саппорт».

## Что выбрать на старте

- **Самый дешёвый старт**: один большой VPS (Hetzner/аналог) + Docker Compose + Caddy. Первые
  10–30 клиентов живут там.
- **Следующий шаг**: провайдер с API и «инстанс = контейнер/машина» — Hetzner Cloud API (дёшево),
  Fly.io (удобно для Docker-приложений; следить за условиями), Azure Container Apps / Cloud Run
  (если ближе Azure/Google; умеют scale-to-zero для триалов).
- **Kubernetes на старте — не нужен**: путь масштаба (GitLab/Supabase), операционно дороже, чем
  полезен при десятках клиентов.
- **Postgres**: один сервер Postgres с базой на клиента (просто и дёшево), не контейнер Postgres
  на клиента.

## Позиционирование (черновик, 2026-08-12, думать дальше)

Ключевой вывод: если на дешёвом тарифе отдавать «просто статику с выключенными нодами»,
преимущества Mars исчезают — на территории сайтбилдеров (Tilda и подобные) нас рвут по всем
пунктам. Ценность Mars — **не «ещё один сайтбилдер», а визуальное программирование**:
автоматизации, боты, данные, API — с CMS в комплекте.

Направления / сценарии, которые определяют лицо продукта (и должны быть в демо и маркетинге):
- **Боты** — Telegram и др., собранные визуальными нодами;
- **Парсеры и автоматизации** — сбор данных, cron-задачи, уведомления, scheduled-обработка;
- **Магазины мелкого бизнеса** — CMS + торговая логика в потоках;
- **Бекенд/API** для мобильных приложений и SPA (headless);
- **Внутренние инструменты** — CRUD поверх данных (посты/метаполя = готовая модель данных),
  дашборды и админки для малых команд (территория Retool/Airtable);
- **Интеграции/«клей»** — связка сервисов, которые у бизнеса уже есть (Telegram, email, CRM,
  базы данных) — территория n8n/Make, но с сайтом в том же месте;
- **IoT** — MQTT-ноды: датчики, теплицы/гаражи/умный дом, дашборды;
- **Агентский ярус** — фрилансеры/агентства собирают клиентам сайты + автоматизацию и продают
  им подписку («свой маленький SaaS поверх Mars Cloud»).

Конкурентный фрейминг: Tilda/Webflow — страницы без программируемой логики (не наша
территория); n8n/Make/Zapier — пайплайны интеграций без сайта/CMS; Bubble — закрытый no-code
с lock-in; Mars — сайт + автоматизация + данные в одной визуальной платформе, open source без
lock-in, с C# там, где нужна полная мощность.

Следствия для облака:
- **Ноды включены на всех тарифах** — это и есть продукт; удешевляем idle-паузой и лимитами,
  а не урезанием возможностей.
- «Супер-дешёвая статика» — не лицо продукта; максимум вспомогательный режим (free/trial,
  «сайт без логики»).
- Демо-инстанс и примеры в маркетинге — боты/автоматизации/магазины, а не «просто блог».
- Always-on нагрузки (MQTT, polling, cron) дороже — учитывать в сетке тарифов.

## Размещение инстансов и тарифы (2026-08-12)

### Мультитенантность (один процесс на много клиентов) — не делаем, обоснование
- Ноды исполняют произвольный C# (Roslyn), плагины — произвольные сборки в дефолтном ALC без
  изоляции, единые `flows.json`, планировщик и `data/` на инстанс — security-границы внутри
  процесса нет, и построить её без переписывания платформы нельзя.
- Профит (2–3× плотности) перекрывается idle-паузой и лёгким overcommit'ом; цена — месяцы
  работы и перманентный риск. Вывод: проблем много, профита ноль.

### Тарифы с Docker — отдельные мини-VM
- Доступ к Docker-демону фактически равен root на хосте — соседям по общей машине его не дать.
- Бонус: гарантированные ресурсы, нет noisy neighbors.

### Дешёвые тарифы — idle-пауза и лимиты, не мультитенант
- Лимиты контейнеров по памяти/CPU на тариф; замерить реальный footprint в спящем режиме и
  время холодного старта.
- **Idle-пауза**: инстанс без активности N минут останавливается и просыпается по первому
  запросу (wake-proxy; платформенно — Fly Machines / Cloud Run scale-to-zero). Спящий контейнер
  почти бесплатен → сотни спящих инстансов на машину. Прокси должен держать запрос, пока
  контейнер стартует.
- Cron тоже может спать: «центральный будильник» контрол-плейна будит инстанс под его задания
  (знает расписания клиентов). MQTT/polling — always-on, отражается в цене тарифа.

### Сетка тарифов
| Тариф | Размещение |
|---|---|
| Дешёвый (сайт + лёгкая автоматизация) | общий узел: контейнер с лимитами + idle-пауза |
| Стандарт | общий узел: контейнер always-on |
| Про/Бизнес (Docker, ресурсы, гарантии) | отдельная мини-VM |
| БД у всех | один Postgres-сервер, база на клиента («мультитенант на уровне БД» — безвреден) |

## Специфичные для Mars моменты

- **Триалы**: 14 дней без карты — инстанс создаётся сразу, биллинг подключается потом (или
  Stripe trial); scale-to-zero провайдеры делают триалы почти бесплатными.
- **Приостановка за неуплату** = остановить контейнер, данные живы — прописать в ToS.
- **Обновления Mars всем клиентам** — rolling update образов; обязателен staging-инстанс, на
  котором версия прогоняется перед раскаткой.
- **Изоляция**: инстансы в отдельной docker-сети, наружу только через прокси; секреты клиентов
  не попадают в свои логи.

## Фазы (когда дойдёт до реализации)

### Фаза 1. MVP-контролплейн на одном VPS
Контрол-плейн — сервис CloudPanel (Blazor Web App) + Keycloak в общем compose моно-репо
Mars.Cloud: вход/регистрация через Keycloak (OIDC, брокеры Google/GitHub), деплой своих
сервисов — publish+rsync+systemd. Оркестратор внутри CloudPanel, `IInstanceProvider` = Docker
на этой же машине (Docker.DotNet или docker CLI), провижининг Mars-контейнера через env-setup,
Caddy wildcard-TLS, ручное создание Stripe-ссылки на оплату. **Готово когда**: по заявке вручную
подтверждённая оплата поднимает клиентский инстанс, доступный по поддомену.

### Фаза 2. Биллинг-автоматизация
Stripe Checkout + Billing + webhooks (или Paddle): оплата → авто-создание, неуплата → пауза,
отмена → удаление после grace. Триалы. **Готово когда**: полный цикл подписки без ручных действий.

### Фаза 3. Надёжность
Ночные pg_dump в объектное хранилище + тест восстановления; мониторинг/алерты инстансов;
staging-инстанс и процесс раскатки новых версий Mars; лимиты ресурсов по тарифам.

### Фаза 4. Рост за один сервер
Вторая реализация `IInstanceProvider` (Hetzner Cloud API / Fly.io / Container Apps), миграция
новых клиентов на неё; мультинодовость; при десятках+ клиентов — оценка Kubernetes.
