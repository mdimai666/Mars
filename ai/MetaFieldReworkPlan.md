## Контекст

Пункт «Стабилизировать PostType MetaFields» из `Product_release_plan.md`. Цель шире стабилизации:
Mars готовится к пользовательским сущностям beyond страниц/новостей — канбан-доски через кастомные
типы, документы в кабинете пользователя и т.п.

Проблемы as-is (исследование 2026-08-22):
- хранение — чистый EAV (`meta_values`, типизированные колонки, сентинелы вместо NULL, нет индексов
  на значениях → фильтрация по мета-значениям фактически невозможна);
- Group/List доделаны на ~30% (`NotImplementedException` в `AsTree`/`MetaFieldTypeToType`, чтение
  flattens через `DistinctBy`);
- Relation-навигации в Mto/QueryLang-пути не заполняются (материализация только в JSON-API через
  `MetaFieldMaterializerService`);
- `selectExpression` Mto — N подзапросов на поле, чтение всех полей всегда целиком;
- статусы — jsonb-блоб в `post_types` + голая строка `posts.status` без целостности;
- определения полей шарятся между типами (M2M) → невозможны per-type настройки.

Индустриальное исследование (Shopify metafields/metaobjects, Pods meta vs table storage, ACF,
Strapi, Directus, + Salesforce/Dataverse/Jira/Odoo/Airtable-клоны): EAV — легаси-паттерн WP,
объекты везде = отдельные сущности/ссылки, вложенные структуры = display-only денормализация.
Учтено: система планируется мультиязычной (логика — по стабильным ключам, отображение — словари).

## Принятые решения (2026-08-22)

1. **Плоские поля.** Group/List удаляются как примитивы хранения; `ParentId` у полей и значений
   упраздняется. «Объекты» и «списки» реализуются связями, не вложенностью.
2. **Объекты = Relation** на PostType/User/File/внешние цели. Доделать: множественные значения
   одного поля, материализацию в Mto/QueryLang-пути.
3. **Список объектов** = дочерний PostType + Relation на родителя + порядок; в редакторе родителя —
   inline-список (заготовки в `FormMetaValueItems`). Сахар «поле-Список», автоматически создающий
   скрытый дочерний тип, — позже, после обкатки явной механики.
4. **Список ссылок** (теги, related) = мульти-значения Relation (строк значений N, порядок по `Index`);
   чтение чинится (убрать `DistinctBy`-потерю).
5. **Вычислимое поле `Query`** (поздняя фаза): хранится только определение (целевой тип + фильтр
   QueryLang c `this`), значение резолвится батчем на чтении; обратная связь («все ссылающиеся на
   меня») — его частный случай.
6. **Select/SelectMany остаются** для закрытых перечислений. Граница: словарь, становящийся объектом
   (свои поля, ссылки из нескольких типов, рантайм-создание) — это PostType + Relation. Варианту
   добавляется стабильный `Key`; в значения денормализуется **Key варианта** (не переводимый Title).
   Title → jsonb-словарь переводов на этапе i18n.
7. **Статусы — системная таблица** `post_statuses (id, post_type_id, title, slug, color, order)`;
   `posts.status_id` FK вместо строки `Status`; jsonb `PostStatusList` мигрирует туда.
   `order`/`color` = схема канбан-доски.
8. **Поле принадлежит типу (1:N).** Шаринг определений убирается; вместо него — клонирование
   «создать из существующего». Общие определения разклонировать, значения перепривязать.
9. **Строгость `Key`**: уникальность в рамках типа, символьный набор `[a-z_][a-z0-9_]*`
   (нормализация при сохранении), переименование разрешено (безопасно: значения ссылаются
   по `MetaFieldId`; view/колонки перегенерируются; для JSON-API это осознанный breaking change).
10. **`Default` реализуем**: хранимое owned-json значение на определении поля; blank-билдер
    подставляет его вместо `NULL = IsNullable`. Для Select дефолт = `Key` варианта.
11. **`ModelName` — ключ провайдера целей** (строка — осознанно: внешние таблицы FK не принимают).
    Валидация по реестру известных целей при сохранении. Префиксная схема: `post[.typeName]`,
    `user`, `file`, `feedback`, `navmenu`, `plugin.<id>.<модель>`, `sql.<dataSourceId>.<таблица>`.
    Переименование PostType → propagation в `ModelName`. Расширяемость — через существующий
    keyed-интерфейс `IMetaRelationModelProviderHandler`.
12. **Чистка `meta_values`**: значениевые колонки nullable, колонка-флаг `NULL` удаляется,
    `Guid.Empty`/дефолт-даты → NULL; `Float (Single)` → `Double`; `type`, `index`,
    `string_short`+`string_text`, `variants_ids` — остаются.
13. **Своя таблица значений на семью владельцев** (замена прежнего решения про единую связку,
    2026-08-22). Вместо общей `meta_values` + трёх join-таблиц — `post_meta_values`,
    `user_meta_values`, `post_category_meta_values`: каждая = FK на владельца (реальный,
    с каскадом) + `meta_field_id` + все значениевые колонки (по решениям Фазы 1:
    nullable, `float8`). Колонки и логика значений (`Get`/`Set`/`Check`/`GetColName`,
    группы типов) живут в базовом классе `MetaValueBase` (обычное C#-наследование,
    в EF базе нет — каждая семья независимо маппится в свою таблицу); сущности семей
    добавляют только ключ владельца. Навигации владельцев — простые one-to-many.
    Новая семья владельцев = новая таблица одной миграцией. Реализация единой связки
    (`meta_value_links` + `owner_kind`) была сделана и отброшена как избыточно сложная
    (обходные хаки EF для полиморфного владельца, ручные догрузки, асимметрия семей).
14. **`Options` jsonb на `meta_fields`** — точка расширения под будущие настройки (UI-подсказки,
    правила валидации, генераторы) без миграций.
15. **Семантика флагов**: `Hidden` = хранится и отдаётся в API, но скрыт в формах;
    `Disabled` = исключён из генерации/форм, значения сохраняются.
16. **PostType не создаёт таблиц/индексов**: все типы живут в общих `posts`; view — генерируемый
    артефакт (по требованию), не данные. Миграции core-схемы пользовательские типы не трогают.
17. **Mto/Roslyn, QueryLang, шаблоны — не трогаем** в этом пласте (кроме вычистки Group/List);
    их упрощение придёт вместе с views.
18. **Grid в админке** (колонки из полей типа + фильтры) — отдельный follow-up после views.

## Фазы

- **Фаза 0 — зачистка Group/List.** Удалить: значения enum 40/50 и все ветки
  (`MetaFieldTypeToType`, `Get()`, `Check()`, `EParentable`, `MetaValueTree` ×2, ветки Group/List
  в `FormMetaValueItems`/`FormMetaField`, записи в `TypeList`/`TypeAsText`, `FieldScheme`,
  закомментированные эксперименты в `FieldsBlank`/`MetaListGetNewGroupChild`/внизу
  `MetaFieldEntity.cs`); `ParentId` упраздняется. Чистка данных НЕ нужна — живых
  инстансов нет, БД пересоздаётся (уточнение 2026-08-22).
- **Фаза 1 — чистка `meta_values`.** Миграция: nullable значениевые колонки, удаление `NULL`-флага,
  конвертация сентинелов в NULL, `float4 → float8`, индексы `(meta_field_id)` +
  `(meta_field_id, string_short)`.
- **Фаза 2 — таблицы значений на семью.** `MetaValueBase` (значениевые колонки +
    `Get`/`Set`/`Check`) + `PostMetaValueEntity`/`UserMetaValueEntity`/
    `PostCategoryMetaValueEntity` (FK владельца); навигации владельцев — one-to-many;
    дифф значений — общий инструмент поверх базы. Миграция: создать три таблицы,
    удалить `meta_values` и старые join-таблицы (переноса данных нет — живых инстансов нет).
- **Фаза 3 — определения полей.** 1:N (миграция общих определений: клоны + перепривязка
  `meta_values.meta_field_id` по типам), строгость `Key`, хранимый `Default` + blank-билдер,
  `Options` jsonb, документация семантики Hidden/Disabled, UI «создать поле из существующего»,
  смена `Type` у поля со значениями — с предупреждением «значения станут ссылаться на пустые
  колонки» и опциональным переносом данных, где он возможен (например int→string).
- **Фаза 4 — Select-варианты.** `Key` у `MetaFieldVariant` (+уникальность в пределах варианта
  поля), запись `Key` варианта в `string_short` при сохранении значения; генерация backfill.
- **Фаза 5 — статусы.** Таблица `post_statuses`, `posts.status_id` FK, backfill строки `Status`
  и jsonb `PostStatusList`, UI редактирования, совместимость DTO (slug через join).
- **Фаза 6 — Relation.** Мульти-значения (чтение списком с порядком), батч-материализация
  в Mto/QueryLang-пути, валидация `ModelName` по реестру целей, propagation при rename типа.
- **Фаза 7 — вычислимое поле `Query`.** Тип поля + определение, батч-резолв на чтении,
  обратная связь как предустановка.
- **Фаза 8 — views (последняя).** Генерация view на PostType по требованию рядом с инвалидацией
  Mto-кэша, чтение через маппинг колонка→свойство, выборочные поля (column pruning). После неё,
  точечно и отдельно: тень-таблицы для горячих типов, затем grid админки.

## Вне скоупа

- Переход на JSONB/реальные таблицы как основное хранение — EAV остаётся source of truth;
  view/тени — только ускорение чтения.
- i18n-словари отображения (Title вариантов/статусов) — отдельная инициатива; сейчас только
  стабильные ключи.
- Переработка MetaModelGenerator/QueryLang — до фазы 8 не трогаем.
- Реестр целей `plugin.*`/`sql.*` — дизайн зафиксирован, реализация по появлении первого потребителя
  (для `sql.*` тогда же решить вопрос не-Guid ключей: `model_id` Guid vs строковая альтернатива).

## Решённые вопросы (раунд 2, 2026-08-22)

1. **Смена `Type` у поля со значениями — разрешена**: предупреждение «значения станут ссылаться
   на пустые колонки» + предложение перенести данные, где это возможно (int→string и т.п.).
   UX — на стороне редактирования поля в админке.
2. **Удаление поля** — cascade значений с подтверждением в UI (подтверждено).
3. **`Float → Double`** — в Фазе 1, одной переписью с nullable-чисткой (подтверждено).
4. **Фронт «списка объектов»** (inline-редактор дочернего типа в карточке родителя) —
   откладываем «на потом»; сама модель (дочерний видимый PostType + Relation) в плане остаётся.
5. `variants_ids` (SelectMany) — остаётся массивом; при потребности фильтрации — GIN-индекс
   (без изменений).
