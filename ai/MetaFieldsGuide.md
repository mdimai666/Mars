## Как устроена подсистема

### Модель

- **Поле принадлежит типу** (`meta_fields` → `post_types`, 1:N). Шаринга
  определений нет; вместо него — «создать из существующего».
- **`Key` поля**: `[a-z_][a-z0-9_]*`, уникален в рамках типа, нормализация при
  сохранении. Переименование безопасно для значений (ссылаются по
  `MetaFieldId`), view/колонки перегенерируются; для JSON-API это осознанный
  breaking change.
- **Значения — по таблице на семью владельцев**: `post_meta_values`,
  `post_category_meta_values`, `user_meta_values`. Общая база `MetaValueBase`
  (значениевые колонки + `Get`/`Set`/`Check`): `string_short`, `string_text`,
  `int`, `long`, `float` (float8), `decimal`, `date_time`, `model_id`
  (Relation/File/Image), `variants_ids` (SelectMany), `index` (порядок
  множественных). Колонки nullable, отсутствие значения = NULL (без
  сентинелов). Новая семья владельцев = новая таблица одной миграцией.
- **Поля плоские.** Group/List/ParentId удалены. Объекты и списки — через
  связи:
  - объект = **Relation** на цель;
  - список объектов = **дочерний PostType + Relation на родителя** + маркер
    `Options.kind = list` (секция детей в карточке родителя);
  - список ссылок (теги, related) = **мульти-значения Relation** (N строк,
    порядок по `Index`).
- **Кратность** — колонка `meta_fields.is_multiple` (default false; свойства
  модели данных — в типизированных колонках, не в Options). Множественное
  поле: N строк значений с `Index`; бланк = ноль строк; сервер отклоняет
  `Index > 0` у одинарных полей. `kind = list` разрешён только множественному
  Relation.
- **Типы полей**: String, Text, Int, Long, Float, Decimal, DateTime, Bool,
  Select, SelectMany, Relation, File, Image, **Query (110)**.
- **Select**: варианты со стабильным `Key`; в значение денормализуется
  **Key варианта** (в `string_short`), не переводимый Title.
- **Цели Relation**: `ModelName` — строковый ключ реестра провайдеров
  (`IMetaRelationModelProviderHandler`, keyed-DI): `post[.typeName]`, `user`,
  `file`, `feedback`, `navmenu`; `plugin.<id>.<модель>` и
  `sql.<dataSourceId>.<таблица>` — дизайн зафиксирован, не реализованы.
  `ModelName` валидируется по реестру; переименование PostType распространяется
  в цели. Строка — осознанно: внешние таблицы FK не принимают.
- **Поле Query**: хранится только определение — `Options` →
  `MetaFieldQueryDefinition` (`target` + `backReferenceKey`, резерв `filter`);
  значение резолвится батчем на чтении (`MetaQueryFieldResolver` →
  `PostJsonService.FillQueryFieldsAsync`). Исключено из Mto-генерации,
  хранимых значений, дефолтов/бланков. Единственный режим — пресет «обратная
  связь»; текст запроса — в бэклоге.
- **`Options` jsonb** — точка расширения поля без миграций. Известные ключи:
  `editor`, `validators`, `generator`, `kind`, `removeMode`, `uploadFolder`,
  `dropZone`, `viewMode`, `featureKey`, `codeLang`. Чтение — через
  типизированные каталоги/ридеры (`MetaFieldKindCatalog`,
  `MetaFieldEditorCatalog`, …), не сырым парсингом.
- **Флаги**: `Hidden` = хранится и отдаётся в API, но скрыт в формах;
  `Disabled` = исключён из генерации/форм, значения сохраняются;
  `IsNullable` = обязательность; `Default` — хранимое значение по умолчанию
  на определении (бланк-билдер подставляет; для Select дефолт = Key варианта).

### Контракты значений

- Публичный ответ: `PostDetailResponse.MetaValues` — словарь «ключ поля →
  массив значений» (одиночные — массив из одного), `Index` отдаётся;
  категории и пользователи остались на словаре одиночных значений.
- Транспорт страницы редактирования — плоский список значений с `Key`/`Index`;
  клиентская модель поста — словарь `(Key, Index)` (`MetaValuesByIndex`).

### Фичи типов и фича-поля

- Фичи: `PostTypeConstants.Features` — `Content`, `Status`,
  `ModifyCreatedDate`, `Language`, `Tags`, `Excerpt`, `Category`, `PostImage`,
  `Single`; хранение — строки в `post_types.enabled_features`.
- Механизм **«фича → поле»**: маркер `Options.featureKey`
  (`FeatureFieldsCatalog`). Фича-поля защищены: бейдж «фича», запрет удаления,
  пикер типа заблокирован (защита считается из «поле == указатель && фича
  включена»).
- **Контент**: фиксированное поле `content` (Type=Text), без колонки-указателя.
  Значение живёт в колонке `posts.Content` (спец-кейс); поле — только
  определение редактора (`Options.editor`), из мета-потоков исключено (формы,
  бланки, валидаторы, генераторы, грид, `PostJsonService`). Рендер в шаблонах:
  `PostTransformer` → процессоры `IPostContentProcessorsLocator` (keyed-DI) по
  ключу редактора. Ключ `content` запрещён к переименованию.
- **Картинка поста**: указатель `post_types.image_field_key` — любое
  Image-поле. Фича включена → указатель обязателен и указывает на поле типа
  Image; поле создаёт клиент (сразу или мини-модалкой выбора). Превью по
  указателю батчатся (`ImagePreviewResolver` в `PostMetaColumnsService`) —
  грид постов, таблица детей, пикеры связей.
- **Single** — тип с ровно одной записью (аналог Strapi single type / Payload
  Globals): автосоздание при первом открытии
  (`PostService.GetOrCreateSingleAsync`, эндпоинт
  `GET api/Post/single/{type}`; Title = Title типа, слаг серверный с числовым
  суффиксом при коллизии), в админке редактор вместо грида, второй пост → 400
  на всех путях создания, удаление записи → 400, включение фичи типу с 2+
  постами → 400. Живёт в общей таблице `posts` — поведение вокруг типа, не
  отдельная сущность.

### Статусы и видимость типов

- **Статусы** — таблица `post_statuses (id, post_type_id, title, slug, color,
  order)` (unique `(post_type_id, slug)`); `posts.status_id` FK
  ON DELETE SET NULL. В запросах/ответах статус — slug
  (`ResolveStatusId`). `order`/`color` — схема канбан-доски.
- **Видимость** — колонка `post_types.visibility`, enum
  `{ Public, Component }`. Компонентные типы фильтруются из списков (флаг
  `IncludeComponent`), исключены из dev-меню, в админке видны под флагом.

### Реестры значений

Все реестры — по паттерну keyed-DI (как провайдеры целей связей).

- **Валидаторы** (правила в `Options.validators`, массив `{type, params}`):
  `MetaFieldValueValidators` — делегат `ValueTask` с
  `MetaValueValidationContext` (модель владельца, ид сохраняемого объекта,
  поле). Встроенные: `regex`, `length`, `unique`. Вызов на всех путях записи:
  посты/категории/пользователи (`MetaValuesValidationExtensions.CustomAsync`),
  JSON-запись постов, генераторы. `unique` — проверка только при сохранении,
  **без DDL**; провайдеры `IMetaValueUniquenessProvider` по доменам
  (`MetaValueOwnerCatalog`: Post/PostCategory/User); провайдер не
  зарегистрирован — правило мягко пропускается; только одиночные скаляры
  (String/Text/Int/Long/Float/Decimal/DateTime). Каталог для UI фильтруется по
  типу поля (`MetaFieldValidatorCatalog.For(type)`).
- **Генераторы** (`Options.generator` `{type, params}`): keyed-обработчики
  `IMetaValueGeneratorHandler`. Встроенные: `sequence` (префикс + паддинг;
  режимы «продолжается» / «сброс каждый день»; словарь категория→префикс по
  slug категорий; счётчики в таблице `meta_sequences`, атомарность =
  уникальный индекс + конкурентный токен с ретраями) и `now`. Вызов в
  `IPostService.Create` после валидации; явно заданные значения не
  перезаписываются; обязательные поля с генератором исключены из проверки
  «значение отсутствует». Перегенерация — XAction
  `mars.content.regenerateGeneratedMetaValues`.
- **Редакторы значений**: серверный каталог `MetaFieldEditorCatalog` +
  фронтовый реестр `IMetaFieldEditorLocator` (ключ → компонент + совместимые
  типы; открытый статический `Register` — точка расширения плагинов). Рендер —
  `DynamicComponent` в `RowMetaValue`; пустой/несовместимый ключ = дефолтный
  редактор типа. **Ключи трёхчастные** `<происхождение>.<семейство>.<реализация>`:
  `core.input.color|url|email|date|time|datetime`, `core.wysiwyg.quilljs`,
  `core.code.monaco` (+ типизированный `Options.codeLang`, дефолт
  `handlebars`), `core.blockeditor.editorjs` (компонент регистрируется в
  админке при старте; где не зарегистрирован — мягкая деградация). Обычный
  текст — без редактора, ключа нет.
- **Тяжёлые редакторы** (WYSIWYG/Code/BlockEditor) — pull-контракт
  `IHeavyMetaValueEditor` (`GetValueAsync`/`SetValueAsync`/`CommitAsync`):
  значение забирается в модель только при сохранении
  (`FormMetaValue.PullAsync` в BeforeSave постов/категорий/пользователей и в
  ИИ-обработке). Лёгкие инлайн-редакторы реактивные.
- **Пикер типа поля** — пресеты `MetaFieldTypePresets` (пресет = тип +
  редактор + кратность/kind/`codeLang`), группы «Текстовые/Числовые/Выбор/
  Даты/Связь» + группа «Raw». Применение пресета = применение настроек; при
  смене типа несовместимые редакторы/правила сбрасываются.

### Админка: грид, дети, загрузка

- **Грид постов**: настройки в `post_type_presentations.grid_settings`
  (jsonb): упорядоченные колонки (базовые ключи `title`, `slug`, `status`,
  `created_at`, `modified_at`, `author` + ключи полей) + колонка и направление
  сортировки по умолчанию; настройка — диалог на гриде и на странице
  презентации типа. Данные: базовые колонки из `posts`, мета-колонки через
  view (`PostTypeViewService.ListFromViewAsync` с сортировкой/пагинацией/
  column pruning). Кастомный `ListViewTemplate` остаётся приоритетным путём
  рендера списка.
- **Фильтры грида**: контракт `PostGridFilter { Key, Op, Value, Values }`
  (contains/eq/in/gte/lte/empty/notEmpty), мета-предикаты expression-деревьями
  (`PostGridMetaFilterExpressions`), фильтрация в
  `PostRepository.ListFilterQueryAsync`; значения сессионные (панель
  `ManagePostFiltersPanel`); транспорт — индексированный query
  `Filters[0].Key=...`; эндпоинты `GET by-type/{type}/list/offset` и
  `POST by-type/{type}/list/page`.
- **Дети** (поле с `kind = list`): секция `MetaValueChildrenList` — таблица
  (колонки = поля детского типа без Query/SelectMany) или карточки
  (`Options.viewMode`: `table` | `cards`; карточка = превью по `ImageFieldKey`
  детского типа + заголовок). «Добавить» = создать ребёнка и привязать /
  привязать существующий; редактирование — боковая панель
  `ChildPostEditorDrawer`; удаление — по `Options.removeMode`
  (`unlink` / `delete-confirm`; дефолт по видимости детского типа: публичный →
  отвязка, компонентный → удаление с подтверждением). Дети — самостоятельные
  посты; порядок свой у каждого родителя; колонки `Order` в `posts` нет.
- **Мульти-редакторы**: множественные Relation — строки с заголовками,
  Файл/Изображение — плитки с превью; драг-порядок (`FluentSortableList` →
  `Index`), пикеры с мультивыбором (медиа-пикер `ModalMediaSelect` умеет режим
  мультивыбора), удаление файлов = отвязка (файл остаётся в медиа).
- **Файлы — две модели**: файл = запись с полями (дроп в секции детей создаёт
  пост-ребёнка на каждый файл) и файл = значение (дроп на плитку
  загружает в медиа и ставит значением, без постов). Папка загрузки поля —
  `Options.uploadFolder` (пусто = папка года). Граница: файлу нужны свои поля
  (подпись, автор…) → детский тип. Общий компонент `MediaUploadZone` (грабля:
  у `FluentInputFile` при заданном `OnInputFileChange` встроенная обработка
  полностью отключается — в авто-режиме делегат не задавать). Видимость
  дроп-зоны — `Options.dropZone` (отсутствие = включена).

### Views

- `PostTypeViewService` генерирует `CREATE OR REPLACE VIEW mt_view_<typeName>`
  **по требованию**: базовые колонки поста + разворот мета-значений
  подзапросами по `meta_field_id` (SelectMany/Query не раскладываются).
  `ListFromViewAsync<T>` — маппинг колонка→свойство, выборочные колонки.
  Инвалидация (drop) при создании/обновлении/удалении типа, рядом с
  инвалидацией Mto-кэша. Имена санитизируются, идентификаторы в SQL
  экранируются кавычками.
- **PostType не создаёт таблиц/индексов**: все типы живут в общих `posts`;
  view — генерируемый артефакт, не данные. Миграции core-схемы пользовательские
  типы не трогают.

## Решения и конвенции — чего придерживаться

1. **EAV остаётся source of truth.** Views/тень-таблицы — только ускорение
   чтения; перехода хранения на JSONB/реальные таблицы не делать.
2. **Плоские поля**: вложенность — через связи (дочерний PostType,
   мульти-значения), не иерархией хранения.
3. **Стабильные ключи для логики, словари для отображения**: денормализуются
   ключи вариантов/статусов, не переводимые заголовки (система планируется
   мультиязычной).
4. **Внешние ключи новых сущностей — только во fluent-конфигурациях**
   (`*EntityConfiguration` провайдера), не атрибутами.
5. **Новые настройки — в существующих jsonb без миграций**; миграции только
   для новых колонок/таблиц.
6. **Свойства модели данных — типизированные колонки** (`IsMultiple`,
   `Visibility`, …); `Options` — только про отображение/поведение редакторов.
7. **Уникальность — валидатор, не DDL**: динамических индексов нет; гонки
   параллельной записи и путь перегенерации приняты без гарантии.
8. **Ключи редакторов трёхчастные** (`core.*`), плагины в будущем — `plugin.*`;
   обычный текст без ключа.
9. **Атомарность sequence** — уникальный индекс + конкурентный токен с
   ретраями (явных транзакций нет: EF InMemory их не поддерживает).
10. **Контент и картинка — фича-поля**: транспорт контента не меняется
    (значение отдельным `post.Content`), поле — только определение редактора;
    фича-поля защищены от удаления/смены типа.
11. **Верификация точечная**: сборка `Mars.slnx` + тесты только затронутых
    клиентов/эндпоинтов, не весь сьют; контракты `WebApiClient` — обязательно
    при ломающих изменениях ответов/реквестов.

## Что было сделано (кратко)

Редизайн 2026-08, всё в ветке `ai/metafields-rework`, детали — в коммитах.

- **Редизайн, Фазы 0–8** (2026-08-22): 0 — удаление Group/List/ParentId;
  1 — чистка `meta_values` (nullable-колонки, сентинелы → NULL, float8,

  `Default`, `Options` jsonb; 4 — стабильный `Key` вариантов Select;
  5 — статусы в таблицу `post_statuses`; 6 — мульти-значения Relation,
  батч-материализация в Mto/QueryLang, реестр целей `ModelName`;
  7 — вычислимое поле Query; 8 — views по требованию.
- **Волна «админка 1»** (2026-08-23): грид с настраиваемыми колонками,
  валидаторы (regex/length), генераторы (sequence/now) с перегенерацией через
  XAction, первая волна редакторов и пресеты типов полей, фильтры грида.
- **Волна «админка 2»** (2026-08-23/24): видимость типов + ломающий контракт
  мульти-значений, `kind=list` + UI детей и мульти-ссылок, `Features.PostImage`
  + общий `MediaUploadZone` + дроп в секции детей, контент как фича-поле +
  вторая волна редакторов (WYSIWYG/Code/BlockEditor), валидатор уникальности.
- **Single-тип** (2026-08-24): автосоздание единственной записи, редактор
  вместо грида, запрет второго поста и удаления.
- **Множественность, файлы, карточки** (2026-08-25): колонка `IsMultiple`,
  матрица редакторов (тип × кратность × kind), дроп файлов без постов,
  мультивыбор в медиа-пикере, режим карточек для детей.

## Бэклог и границы

### Отложено «по появлении потребности»

- Уникальность мульти-значений (семантика не определена).
- Указатель «заголовок-подпись» для свёрнутых строк значений.
- Ленивая инициализация тяжёлых редакторов — после редизайна форм.
- Query-определения текстом запроса с опорой на `this` (бывшая Фаза Е);
  пресет «обратная связь» остаётся единственным режимом.
- Разделение DateTime на DateOnly/TimeOnly.
- i18n-переводы заголовков вариантов/статусов (ключи уже есть; завязано на
  инициативу мультиязычности).
- Реестр целей `plugin.*`/`sql.*` (для `sql.*` решить вопрос не-Guid ключей:
  `model_id` Guid vs строковая альтернатива).
- Расширение валидаторов/генераторов/редакторов из плагинов (первая волна
  встроенная).
- Тень-таблицы горячих типов.

### Отложено с привязкой к другим инициативам

- Ветвление Mto/генераторов по `IsMultiple` (одинарная навигация против
  коллекции) — с приходом упрощения генераторов.
- Переработка MetaModelGenerator/QueryLang — до отдельного решения.

### Вектор развития

- Системные поля (заголовок и остальные) через механизм мета-полей: те же
  правила — валидаторы, порядок, скрытие, генераторы. Контент уже фича-поле.
- Все поля формы объекта — как метаполя: единый рендер и настройка
  (переупорядочивание, скрытие, редакторы из реестра).

### Отклонено (границы — не делать без пересмотра)

- Серверный батч-резолв превью в ответе редактирования — плитки запрашивают
  файл сами.
- Бэкфилл существующих Relation-полей в множественные — дефолт
  `IsMultiple=false` принят как смена поведения.
- Пер-элементные атрибуты файлов (подпись/альт) без детского типа.
- Переезд `kind` в колонку — нужен только фронту; понадобится серверу — одной
  миграцией.
- Переход на JSONB/реальные таблицы как основное хранение.
- Пер-постовый маркер формата значения контента — формат всегда = текущий
  редактор типа.
