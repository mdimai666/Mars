## Контекст

После Фазы 2: грид с настраиваемыми колонками и фильтрами, валидаторы
(`Options.validators`), генераторы (`Options.generator`, `meta_sequences`), каталог
редакторов первой волны (`Options.editor` → `IMetaFieldEditorLocator`, цвет/url/
email/дата/время), пресеты типов полей.

Пробелы, зафиксированные разведкой 2026-08-23:
- мульти-значения поддерживаются контрактами на запись (`MetaValueDetailBase.Index`),
  но админка рендерит только `Index == 0` (`FormMetaValueItems`); в респонсах
  `PostResponse.MetaValues` — словарь «поле → одно значение», `Index` закомментирован;
- нет ни инлайн-детей, ни вообще отображения дочерних постов;
- у контента 4 редактора (`PlainText`/`WYSIWYG`/`Code`-Monaco/`BlockEditor`-Editor.js),
  выбор в `PostType.PostContentSettings` — отдельно от реестра редакторов мета-полей;
- пикер медиа строго одиночный; зона загрузки `FluentInputFile` в
  `FluentMediaFilesList` с захардкоженным `MaximumFileCount="4"`; тот же паттерн
  продублирован в `ZipUploadDialog`; `GalleryFluentFileUploader1` — мёртвый код;
- `FluentSortableList` уже используется в админке (`FormsBuilderPage`) — drag-reorder доступен;
- на `PostTypeEntity` старый хинт-комментарий `//icon, in_menu, search, public`.

UX-исследование (проверено по докам 2026-08-23): паттерн популярных продуктов для
вложенных объектов — **список свёрнутых строк/карточек + режимы отображения +
редактирование в боковой панели (drawer), не в модалке** (ACF Repeater: layout
Table/Block/Row, сворачивание строк, лимиты; ACF Gallery: сетка превью + панель
элемента; Strapi: «Add an entry», drag&drop строк; Payload Array: свёрнутые карточки
с RowLabel, drag-сортировка по умолчанию; Directus/Airtable: drawer для связанных
записей). Отсюда: инлайн «всё сразу» не делаем — таблица + drawer, карточки потом.

## Принятые решения (2026-08-23)

1. **Список детей = мульти-значение Relation-поля на стороне родителя** (строки
   `{ModelId, Index}` в таблице значений). Дети — самостоятельные посты, на их
   стороне ничего не пишется; порядок свой у каждого родителя; один ребёнок может
   входить в списки нескольких родителей. Колонку `Order` в `PostEntity` не
   добавлять (явное решение пользователя).
2. **Мульти-значения в ответах — массив под ключом** (стандарт индустрии:
   Strapi, Directus, Payload, ACF REST; плоские ключи `photo[0]` — только внутри
   HTML-форм и внутреннего хранения WP-меты). Публичный респонс меняется ломающе,
   без совместимости (альфа). Транспорт страницы редактирования — плоский список
   с `Key` и `Index`; клиент собирает словарь с ключом `(Key, Index)`.
3. **Видимость типа — enum `PostTypeVisibility { Public, Component }`**, колонка +
   миграция (хранение по конвенции `EMetaFieldType`). Компонентные типы видны в
   админке под флагом. **Single-тип** (аналог ACF Options page / Pods single) —
   следующий этап, отдельное поле + автосоздание поста при первом открытии.
4. **Маркер списка — явный, не вывод из условий**: `Options.kind = list` на
   Relation-поле (типизированное чтение + пресет «Список объектов» в пикере).
   Рендер этого этапа — таблица + drawer (боковая панель с формой поста);
   карточки — следующий этап.
5. **Удаление ребёнка из списка** — `Options.removeMode` (`unlink` /
   `delete-confirm`); дефолт по видимости типа-цели: публичный → отвязка,
   компонентный → удаление с подтверждением; переопределяется на уровне поля.
6. **`Features.PostImage`**: при включении автосоздаётся системное неудаляемое
   поле `Image` (ключ `image`) и устанавливается указатель картинки типа.
   Превью через указатель — в рамках этого плана: миниатюра в таблице детей,
   в строках/пикере мульти-ссылок, колонка грида постов.
7. **Загрузка**: общий компонент `MediaUploadZone` (рефакторинг: убрать
   `MaximumFileCount=4`, выпилить логику из `FluentMediaFilesList`, заменить копию
   в `ZipUploadDialog`, удалить мёртвый `GalleryFluentFileUploader1`); папка
   загрузки для полей Файл/Изображение — в `Options` поля (пусто = папка года).
   Дроп файлов в секцию детей = загрузка в папку + создание ребёнка + связь.
8. **Контент**: колонка `posts.Content` остаётся (скорость; фича-флаги как есть).
   Системное неудаляемое поле `content` (Type=Text) на типах с `Features.Content` —
   только определение редактора (`Options.editor`, `Options.codeLang`); значение
   пишется в колонку спец-кейсом. `PostContentSettings` сносится с data-миграцией.
   Общий механизм «фича → системное поле» для `Content` и `PostImage`.
9. **Вторая волна редакторов**: `WYSIWYG` / `Code` / `BlockEditor` в
   `MetaFieldEditorCatalog` для `String`/`Text`. `Code` — типизированный
   `Options.codeLang` с селектором языков (код пишет человек — удобно, а не
   JSON-проброс). Тяжёлые редакторы инициализируются как есть; ленивость — после
   редизайна форм. Рендер значения — через существующий `IPostTransformer`
   (в шаблонах на выбор: рендер или сырое значение); в админке пока сырое.
10. **Уникальность**: валидатор `unique` в существующем реестре, скоуп = весь тип
    поста; серверная проверка при записи + динамический уникальный индекс на поле
    (управляется при включении/выключении правила); только одиночные скалярные
    значения.
11. **Конвенции**: внешние ключи новых сущностей — только во fluent-конфигурациях;
    новые настройки в существующих jsonb — без миграций; миграции только для новых
    колонок/таблиц.

## Фазы

Порядок: 1 → 2 → 3 (2 и 3 слабо связаны, можно менять местами) → 4 → 5.

- **Фаза 1 — контракты мульти-значений и видимость типов.** Миграция: колонка
  `Visibility` на `PostTypeEntity` (enum, default `Public`). Респонсы:
  `PostResponse.MetaValues` → словарь «ключ поля → массив значений» (в
  `MetaValueResponse` раскомментировать/добавить `Index`); проверить и поправить
  всех потребителей (админка, фронт-шаблоны, `WebApiClient`-модели). Страница
  редактирования: транспорт — плоский список значений, в клиентской модели —
  словарь `(Key, Index)` (одиночные читаются как `(key, 0)`). Админка: селект
  видимости в `EditPostTypePage`, флаг «показывать компонентные типы» в списке
  типов, компонентные типы не попадают в меню создания постов.
- **Фаза 2 — вид «Список» и UI детей/мульти-ссылок.** Маркер `Options.kind = list`
  (типизированное чтение на сервере и фронте) + пресет «Список объектов» в пикере
  типов полей (Relation + kind list). Мульти-отношение в форме поста: строки
  связанных постов с заголовками, `FluentSortableList` (порядок → `Index`),
  добавление через расширенный до мультивыбора диалог-пикер (чекбоксы + «добавить
  выбранные»), удаление по `removeMode`. Секция детей в карточке родителя
  (поле-список): таблица детей (колонки = поля ребёнка), «Добавить» = создать пост
  ребёнка и сразу привязать; редактирование — **боковая панель** (адаптация
  `EditPostView` в режим панели); удаление из списка по `removeMode` (отвязка /
  удаление ребёнка с подтверждением). Привязать можно и существующий пост-цель.
- **Фаза 3 — PostImage и загрузка.** Миграция: колонка `ImageFieldKey` (nullable)
  на `PostTypeEntity`. `Features.PostImage`: включение автосоздаёт системное поле
  `Image` и пишет указатель; механизм «фича → системное поле» общий с Фазой 4
  (маркер неудаляемости — `Options.systemKey` на поле, без миграции). Превью по
  указателю: миниатюра в таблице детей (Фаза 2) и в строках/пикере
  мульти-отношений; базовая колонка `image` в настройках грида постов
  (`PostTypeGridSettings`, форматирование URL в `PostMetaColumnsService`).
  Рефакторинг зоны загрузки: общий `MediaUploadZone` (кратность, лимит, accept,
  папка, колбэк «файлы загружены») на штатном `FluentInputFile`; папка загрузки в
  `Options` полей Файл/Изображение (пикер папок медиа в форме поля; пусто = папка
  года). Дроп файлов в секцию детей: загрузка в настроенную папку → на каждый файл
  создаётся пост-ребёнок со значением Файл/Изображение и связью к родителю.
- **Фаза 4 — контент и волна редакторов.** Реестр `MetaFieldEditorCatalog` +=
  `WYSIWYG`, `Code`, `BlockEditor` (совместимые типы `String`/`Text`; компоненты
  уже существуют: `WysiwygEditor`, `CodeEditor2`, `BlockEditor1`); у `Code` —
  типизированный `Options.codeLang` с селектором языков. Системное поле `content`
  (Type=Text, `Options.systemKey`) автосоздаётся на типах с `Features.Content`;
  значение — колонка `posts.Content` (спец-кейс чтения/записи); редактор контента
  в админке берётся из `Options.editor` поля. Пресеты пикера: «Текст (Editor.js)»,
  «Текст (WYSIWYG)», «Код». Миграция: data-перенос `PostContentType`/`CodeLang` в
  Options поля `content`; удаление `PostContentSettings` (owned-тип, UI и
  эндпоинты презентации типа).
- **Фаза 5 — уникальность.** Валидатор `unique` в реестре `MetaFieldValueValidators`
  (интерфейс расширяется контекстом: поле, пост, доступ к БД); проверка при записи
  значений на общем пути (админка + JSON-API), ошибка «значение уже занято».
  Динамический уникальный индекс: при включении правила создаётся
  `CREATE UNIQUE INDEX … (колонка типа) WHERE "MetaFieldId" = '<id>' AND <колонка>
  IS NOT NULL` (raw SQL, по конвенции индексов-выражений), при выключении —
  удаляется; конфликт индекса → 400. В каталоге валидаторов и форме поля —
  правило «уникальное значение». Только одиночные скалярные значения.

## Верификация (правило: точечно, не весь сьют)

Общий build `Mars.slnx`; по каждой фазе — только затронутые тесты:
- Фаза 1: юнит `Test.Mars.Host` на маппинг мульти-значений; интеграционные
  `posttypes`/`posts`; **`WebApiClient`-контракты обязательно** (форма респонса
  меняется ломающе); точечно проверить фронт-шаблоны, потребляющие `MetaValues`
  (без полного прогона).
- Фазы 2–3: новые эндпоинты/клиенты, затронутые (`PostMetaColumnsService` для
  колонки `image`); зона загрузки и дроп — визуально при разработке.
- Фаза 4: юнит реестра редакторов и автосоздания системных полей; интеграционные
  `posttypes` (снос `PostContentSettings`); контракты презентации типа.
- Фаза 5: юнит валидатора + интеграционный конфликт (повторное значение → 400).
- Админка — визуально при разработке, отдельным прогоном не проверять.

## Вне скоупа

- режим карточек в секциях детей — следующий этап (превью через `ImageFieldKey`);
- Single-тип (отдельное поле, автосоздание поста при первом открытии) — следующий этап;
- ленивая инициализация тяжёлых редакторов — после редизайна форм;
- указатель «заголовок-подпись» для свёрнутых строк — по появлении потребности;
- уникальность мульти-значений;
- «только при необходимости» (из Фазы 2): Фаза Е (Query-определения текстом
  запроса), разделение DateTime на DateOnly/TimeOnly, i18n вариантов/статусов,
  реестр целей `plugin.*`/`sql.*`, тень-таблицы, хуки пре-/пост-обработки типов.
